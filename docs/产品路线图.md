# 灵阅产品路线图

> 文档状态：M1-A/M1-C 已完成实现和 Pixel_9 验收；M1-B 实现完成，尚需补充 10 MB 以上文件的明确设备验收记录；M2 Front Matter 首个切片已完成，下一步推进本地图片与附件  
> 更新时间：2026-08-09（北京时间）  
> 当前版本基线：`v0.1.17`

## 1. 产品定位

灵阅是一款面向开发者的 Android 通用源代码阅读与轻量编辑工具。

核心场景是：在手机上稳定打开主流编程语言项目和 Markdown 文档，快速浏览目录、搜索内容、定位代码，并在需要时进行小范围修改。

产品优先级为：

1. 源码阅读可靠性
2. 项目和文件导航效率
3. Markdown 高级文档阅读
4. 轻量编辑
5. Git 和项目管理

灵阅不以移动端完整 IDE 为目标，不承担编译、调试、运行项目和完整 LSP 开发环境的职责。

## 2. 当前能力基线

### 2.1 已实现能力

- 支持 `ACTION_VIEW`、`ACTION_EDIT`、`ACTION_SEND` 外部文件入口。
- 支持 SAF 单文件、SAF 目录、ZIP 导入、公共 HTTPS Git 仓库和内置示例。
- 目录、ZIP、Git 和本地项目使用统一的项目索引和可折叠目录树。
- 支持最近项目、项目全局搜索、文件内搜索、搜索命中高亮和快速文件切换。
- 支持多文件标签页，每个标签页独立保存草稿、编辑状态和 Markdown 预览状态。
- 使用 Sora Editor 和 TextMate 实现源码编辑、行号、语法高亮、跳转到行和自动换行。
- 当前有约 78 种文件类型映射，覆盖主流语言、脚本、配置和工程文件；其中 73 个带独立 grammar 的类型纳入语义 token 回归。
- Markdown 支持源码/预览切换、YAML Front Matter 折叠、表格、任务列表、脚注、代码块高亮、KaTeX 数学公式、Mermaid 流程图、目录跳转和代码复制。
- 大文件阈值和整文件读取上限会按设备内存预算动态决策；大文件进入分段只读模式，Git 克隆和更新提供阶段反馈、进度和取消入口。
- 支持字号、阅读背景、应用配色、明暗主题和在线更新。

### 2.2 当前明确边界

- 已支持 UTF-8、UTF-8 BOM、UTF-16、GB18030/GBK、Big5、Latin-1 自动识别和手动切换；后续仍需增加编码置信度提示及项目级默认编码。
- 大文件阈值会按设备内存动态落在 512 KB—1 MB，进入分段模式后不能编辑和覆盖保存；整文件读取预算动态落在 8—20 MB。
- 项目全局搜索按编码流式扫描文件全文，不再跳过大于 2 MB 的源码；每个文件最多返回 8 个命中，全局最多返回 200 条。
- Git 当前仅支持公开 HTTPS 仓库、浅克隆和安全快进更新，不支持 SSH、Token、私有仓库、分支、Tag、Commit 历史和 Diff。
- Markdown 预览使用 APK 内置离线资源，网络加载被禁用；本地图片、相对路径附件和外部资源支持不完整。
- 编辑器尚未形成完整的查找替换、撤销/重做、自动缩进、草稿恢复工作流。

### 2.3 综合审计结论

- 当前架构与产品定位匹配，无需推倒重来：Compose 承载产品界面和数据源管理，Sora Editor 负责普通源码阅读，WebView 只负责 Markdown 高级渲染。
- 当前主要短板不是“语言数量不够”，而是 Markdown 本地资源与位置同步、轻量编辑闭环和 Git 高级生命周期仍需要补齐；M1 阅读主链路只保留 10 MB 以上文件的验收补证。
- 产品已经完成“打开、阅读、导航、搜索、继续阅读”的首轮主链路，当前优先扩展 Markdown，再补齐轻量编辑和 Git，最后投入符号大纲、结构化视图等差异化能力。
- 不将完整 IDE、LSP、编译、调试和运行环境纳入近期范围，避免功能膨胀影响移动端的打开速度和阅读体验。

### 2.5 产品审计结论摘要

本次审计的核心结论是：灵阅应先成为“可靠、快速、可持续阅读源码和 Markdown 的移动阅读器”，再逐步增加编辑、Git 和结构化能力。功能数量不是第一目标，打开速度、阅读位置、搜索精度、离线可用性和失败恢复才是长期体验的基础。

按用户价值和实现风险，结论收敛为四条执行原则：

1. **先打通阅读主链路（P0）**：来源统一、编码可靠、大文件可读、项目索引完整、文件内/项目搜索可定位、切换后能继续上次阅读。
2. **再补齐 Markdown 和轻量编辑（P1）**：本地资源、预览缓存、源码/预览同步，以及可撤销、可恢复的小范围修改。
3. **最后扩展 Git 和开发者增强（P2）**：认证、分支、Diff、冲突、符号大纲和结构化视图都应建立在稳定阅读内核之上。
4. **质量能力横向贯穿**：统一弹层和导航、紧凑信息密度、无障碍语义、性能观测、隐私与缓存治理，以及仅使用 Pixel_9 模拟器的回归门禁。

审计中明确不把灵阅做成移动端完整 IDE：编译、调试、运行、完整 LSP 和复杂重构不进入近期路线，以免大型依赖和后台任务拖慢“打开即读”的核心体验。

| 能力域 | 要解决的核心问题 | 优先级 | 里程碑 | 交付边界 |
| --- | --- | --- | --- | --- |
| 来源与打开 | 文件来自本地、SAF、ZIP、Git 或分享入口时，都能可靠打开并说明读写能力 | P0 | M1-A、M1-B | 统一来源抽象、编码识别、权限/失败恢复、项目导入与完整索引 |
| 项目导航 | 多文件项目中快速找到文件，切换后不丢上下文 | P0 | M1-B、M1-C | 可折叠目录树、最近项目、快速文件切换、当前文件定位、完整路径复制 |

| 持续阅读 | 退出、切换标签或重启后继续上次阅读 | P0 | M1-C | 最近阅读行、滚动位置、文件书签/行书签、标签页独立状态和安全恢复 |

| 轻量编辑 | 偶发的小范围修复不丢草稿、不破坏原文件 | P1 | M3 | 撤销/重做、查找替换、自动缩进、草稿恢复、保存反馈和只读原因说明 |
| Git 生命周期 | 已导入仓库可以安全地持续跟踪，而不是只能首次克隆 | P2 | M4 | 认证、分支/Tag、刷新、Diff、修改保护、冲突查看、离线缓存和错误分类 |
| 开发者增强 | 在“阅读器”定位下提供比普通文本查看器更高效的结构化阅读 | P2 | M5 | 符号大纲、TODO/日志模式、JSON/YAML/XML/TOML 结构视图、多项目工作区和大屏适配 |
| 产品质量 | 长时间使用稳定、界面一致且可维护 | 横向 | M1—M5 | 紧凑统一的弹层与导航、阅读设置与在线更新、性能监控、无障碍语义、隐私/缓存治理、Pixel_9 回归和离线验证 |

执行顺序固定为“来源与打开 → 导航与搜索 → 持续阅读 → Markdown → 轻量编辑 → Git → 差异化能力”。格式支持只作为能力域的输入，不单独以“新增语言数量”作为版本目标；新增格式必须同时补充识别、打开、搜索、高亮/渲染和回归样例。

阶段完成的判定采用双状态记录：

- **实现状态**：代码路径和自动化测试已具备。
- **验收状态**：在指定 Pixel_9 模拟器完成回归，并覆盖离线、异常恢复和大文件场景。

只有两种状态都满足时，才能把里程碑标记为“完成”并进入 Release；设备掉线或只完成定向测试时，路线图保留为“实现完成、验收待补”。

### 2.7 审计结论对应的执行队列

为避免每一轮继续横向堆叠功能，后续按以下顺序推进。每一项完成后先形成可独立验证的垂直切片，再进入下一项：

| 顺序 | 近期工作包 | 主要交付 | 完成信号 |
| --- | --- | --- | --- |
| 1（已完成） | M1-C 搜索与大文件闭环 | 流式文件内搜索、搜索取消/进度、精确行列跳转、跨标签上下文恢复 | 已通过 Pixel_9 47/47 instrumentation；M1-B 另补 10 MB+ 文件验收 |
| 2（当前） | M2 Markdown 本地资源与同步 | Front Matter 已完成；继续图片/附件、预览缓存、源码/预览位置同步和错误回退 | 离线 README 和设计文档可完整阅读，切换不白屏、不丢位置 |
| 3 | M3 安全轻量编辑 | 撤销/重做、查找替换、草稿恢复、原子保存和只读替代操作 | 小范围修改可逆、可恢复，保存失败不破坏原文件 |
| 4 | M4 Git 生命周期 | 认证、分支/Tag、Diff、冲突查看、缓存治理和错误分类 | 更新前能看到变化，不静默覆盖本地修改 |
| 5 | M5 开发者差异化 | 符号/TODO/日志导航、结构化视图、多项目工作区和大屏适配 | 复杂项目中定位速度明显优于普通文本查看器 |

所有工作包都必须同时补充：最小失败回退、性能边界、离线行为、可访问语义和自动化回归样例；只增加语法或文件格式而没有对应阅读体验提升的工作不单独立项。

## 3. 产品原则

- 阅读优先：任何新增能力都不能以牺牲打开速度、滚动稳定性和可读性为代价。
- 离线优先：已导入的文件和项目在无网络状态下仍可继续阅读。
- 来源解耦：Local File、SAF、ZIP、Git Working Tree 和内置示例统一通过来源能力接口提供数据。
- 能力透明：明确显示来源是否可读、可写、可搜索、可刷新和可删除。
- 失败可恢复：网络失败、权限失效、编码异常、索引失败和文件消失都必须提供下一步操作。
- 小步发布：每个阶段形成可独立验证和发布的垂直切片，不把多个高风险能力绑定到同一版本。

实施记录（第一切片，2026-08-08）：

- `ReadingDocumentState` 独立保存文档稳定 ID、来源、项目根、最近行号、文件书签和行书签；最多保留 200 个文档、每个文档最多 100 个行书签。

## 5. 版本策略

- `0.x` 阶段已完成 M1 首轮主链路，当前优先推进 M2；M1-B 的 10 MB+ 验收补证作为发布门禁并行完成。
- M2 和 M3 可以并行开发，但 Markdown 预览稳定性优先于编辑器高级能力。
- M4 涉及认证、凭证和仓库安全，应单独设计并增加安全审查。
- M5 只在前四个阶段稳定后推进，避免过早引入 LSP、复杂解析器和大型依赖。
- 每个阶段发布前必须补充 Pixel_9 模拟器验证、离线验证和回归清单；不使用 Redmi Note 8 Pro 真机验证本项目。

## 6. 暂不优先

- 编译、运行和调试 Android/Java/Go/Rust 项目。
